# 项目开发铁律（所有项目通用）

> 目的：防止 AI 频繁改出 Bug、效率低下的问题。
> 核心理念：**先定规范再写代码，先管流程再谈效率。**

---

## 一、总原则（4条铁律）

1. **先文档，后代码** — 需求、设计、规则先写成文档，确认后再动代码
2. **小步修改，每步验证** — 一次只改一件事，改完必须自测通过才继续
3. **测试是安全网** — 没有测试保护的改动 = 裸奔改代码
4. **版本可回溯** — 任何时刻都能回到上一个正常版本

---

## 二、需求变更流程（防止"说不清就动手"）

```
用户提出想法
  → 1. 写进需求文档（记录原话，不加工）
  → 2. 讨论确认（问清楚：做什么/不做什么/验收标准）
  → 3. 写设计/规则文档（含边界情况）
  → 4. 确认后 → 才开始改代码
```

**违反示例**：用户说"加个功能" → AI 直接写代码 → 功能不对 → 改 → 又不对 → 改乱了
**正确做法**：先问清"这个功能具体什么样？边界情况怎么处理？" → 写文档 → 确认 → 实现

---

## 三、TDD 测试驱动开发（防止"改出 Bug 不知道"）

### 3.1 强制流程（Red-Green-Refactor）

```
红（Red）    ：先写测试，运行确认是失败的（证明测试有效）
绿（Green）  ：写最小代码让测试通过
重构（Refactor）：清理代码，再跑测试确认没改坏
```

### 3.2 每次改动的自测要求

1. **跑通**：代码能运行，无报错
2. **回归**：跑已有的全部测试，确认没改坏别的东西
3. **边界**：测试空数据、异常数据、极端值
4. **对比**：业务逻辑改动，用固定样本对比改动前后结果（见回测）

### 3.3 测试优先级

| 类型 | 覆盖什么 | 必做程度 |
|------|---------|---------|
| 单元测试 | 单个函数逻辑 | ✅ 必须 |
| 回归测试 | 改完确认老功能没坏 | ✅ 必须 |
| 回测（业务类） | 判定规则/策略改动 | ✅ 必须 |
| 集成测试 | 多模块配合 | ⚠️ 有条件做 |

## 四、版本管理（防止"改来改去回不去"）

### 4.1 提交规范

- 每次有意义的改动后必须 commit
- 格式：`类型: 描述`（feat/fix/refactor/docs/style/test）
- 一个 commit 只做一件事
- **改代码前先确认 git 干净**（git status）

### 4.2 回退流程（出问题怎么办）

```
1. git log 找到上次正常版本号
2. 对比当前代码和正常版本的差异（git diff）
3. 确认问题来源
4. 回退：git revert 或 git checkout
5. 修复后重新提交
```

---

## 五、守护规则（Guardrails — 防 AI 乱来）

### 5.1 对 AI 的硬性约束

1. **不改没被要求改的代码** — 禁止顺手重构、顺手"优化"无关代码
2. **改完必须自测** — 不允许"改完不跑就交付"
3. **不绕过测试** — 禁止为了"让测试通过"而删测试/改测试标准
4. **不删历史数据** — 回测样本、文档记录永久保留
5. **大改动先备份** — 改核心逻辑前，先 commit 当前状态

### 5.2 对 AI 的软性要求

1. **先解释再动手** — 复杂改动先说明"我要改什么、为什么"
2. **小步迭代** — 一次改动控制在小范围，便于定位问题
3. **明确边界** — 需求不清楚时先问，不要猜
4. **保留决策记录** — 规则/阈值调整记录原因，方便追溯

## 六、文档管理（防止"决策丢失"）

```
每个项目必须有：
├── docs/
│   ├── requirements.md  # 需求文档（用户原话 + 确认结果）
│   ├── design.md        # 设计文档（架构、规则、界面）
│   └── CHANGELOG.md     # 变更日志（每次改动记录）
```

**CHANGELOG 格式**：
```
## 2026-08-02
- 新增：极端波动状态判定（ATR%>20%）
- 修改：超跌反弹阈值从 ATR%>10% 调整为 >20%
  - 原因：KOMA(18%)被误封杀，山寨币高波动是常态
  - 回测：4/4 通过
```

---

## 七、验收清单（每次交付前过一遍）

- [ ] 需求是否写进文档并确认？
- [ ] 代码是否提交 git？
- [ ] 是否跑了全部测试/回测？
- [ ] 是否测试了边界情况？
- [ ] 改动是否只涉及被要求的部分？
- [ ] CHANGELOG 是否更新？
- [ ] 是否有留下回测数据样本？

---

## 八、这套规则怎么落地

1. **把本文档放在每个项目根目录**（如 `docs/PROJECT_RULES.md`）
2. 每次开发会话开始，先读这份规则
3. AI 每次动手前对照规则自查
4. 用户发现 AI 违规，直接指出"违反第X条"
